# CampusMate 注册、登录与认证草图设计

日期：2026-09-09

## 1. 目标与边界

本次创建独立的可点击认证草图，用于验证注册、登录、校园身份认证、组织认证和角色授权之间的关系。草图不连接真实接口、不保存真实凭据、不上传证明材料，也不修改现有 `apps/web/src/pages/Login.tsx`。

草图输出到 `work/campusmate-design/CampusMate-auth-prototype.html`，并从认证成功或“暂不认证”状态提供进入现有交互草图的入口。

## 2. 核心原则

1. 创建账号不等于校园认证。
2. 校园认证不等于组织认证。
3. 组织认证不等于用户自动成为负责人或发布者。
4. 未登录用户和未认证账号可以浏览公开内容；发布、申请、查看联系方式等操作需要校园认证。
5. 组织负责人只能管理自己所属组织的成员与发布者；角色有有效期、可撤销、可复核。
6. 认证证明材料不进入公开资料，也不发送给 AI。

## 3. 页面与状态

### 3.1 登录

- 品牌、账号输入和登录方式是首屏主要内容，不使用营销型 Hero。
- 使用分段控件切换“密码登录”和“验证码登录”。两种方式各自显示必要字段，避免当前界面同时展示密码与验证码造成歧义。
- 提供“忘记密码”和“暂不登录，浏览公开内容”。
- 草图中的账号和验证码均为虚构值，提交后只改变本地演示状态。

### 3.2 注册账号

- 第一步填写手机号或邮箱、验证码和新密码，创建未认证账号。
- 第二步填写昵称；专业、年级和技能允许稍后完善，减少首次注册阻力。
- 注册成功后进入校园认证引导，而不是直接获得发帖权限。

### 3.3 校园认证

- 优先展示校园邮箱；预留学校统一身份认证入口。
- 支持“稍后认证，先浏览”，但明确列出认证后解锁的发布和申请权限。
- 成功后状态从 `unverified` 变为 `campus_verified`。
- 正式实现必须校验学校域名白名单、验证码用途、过期时间、频率和尝试次数。

### 3.4 认证中心

认证中心分三个并列层级：

| 层级 | 证明内容 | 结果 |
| --- | --- | --- |
| 校园身份 | 校园邮箱或学校统一身份 | 校园认证用户 |
| 组织资质 | 官方页面、学院/书院证明、指导教师确认等 | 认证组织 |
| 角色授权 | 已核验负责人发出的站内邀请 | 组织成员、负责人或发布者 |

组织认证流程为：提交申请 → 官方页面或证明核验 → 私有上传/填写材料 → 人工审核 → 设置有效期 → 到期复核。组织审核通过后，负责人才能邀请成员和发布者。

### 3.5 组织申请

- 选择组织类型：学院/书院、学生组织、社团。
- 填写标准组织名称、学校归属、官方页面、负责人身份和说明。
- 草图只显示文件选择占位，不读取或上传本地文件。
- 提交后展示审核中状态、申请编号、预计处理时间和撤回入口的设计位置。

### 3.6 角色邀请

- 已核验负责人可输入校园账号并选择“成员”或“发布者”。
- 邀请对象需要站内接受后角色才生效。
- 发布者权限限定在该组织，必须显示有效期。
- 草图演示邀请预览，不发送消息、不修改真实权限。

## 4. 交互流

```text
公开浏览
  ├─ 登录 → 已登录账号 → 进入发现页
  └─ 注册 → 创建未认证账号 → 完善资料 → 校园认证
                                      ├─ 成功 → 解锁发布与申请
                                      └─ 稍后认证 → 仅浏览

认证中心
  ├─ 校园身份状态
  ├─ 组织认证申请 → 人工审核 → 有效期 / 复核
  └─ 已认证组织 → 负责人邀请 → 成员接受 → 角色生效
```

页面需要支持返回上一步、取消、刷新后恢复默认演示、服务异常、验证码发送中/倒计时、字段错误和审核被驳回等状态。

## 5. 视觉方案

- 沿用现有草图的白底、深绿色主操作和蓝/绿/淡紫状态色，避免大面积渐变和装饰性背景。
- 桌面端使用左侧窄流程导航与右侧主表单；手机端改为顶部步骤条和单列内容。
- 认证层级使用三个并列状态区，不把组织认证嵌套在注册表单卡片中。
- 所有状态同时使用文字和图标，不仅依赖颜色。
- 主要按钮固定在表单底部；次要动作使用文本按钮，危险动作与主操作分开。

## 6. 草图状态模型

```text
session:
  authView: login | register_account | register_profile | campus_verify | identity_center
  loginMode: password | code
  accountStatus: visitor | unverified | campus_verified
  campusVerification: idle | code_sent | verified | failed
  organizationApplication: none | draft | reviewing | approved | rejected | expired
  organizationRole: none | member | publisher | owner
```

状态转换由本地纯函数完成，并为以下行为编写测试：

- 注册后保持未认证，不能获得发布权限。
- 校园认证后解锁学生发布与申请，但不获得组织发布权。
- 组织审核通过后仍须负责人邀请，普通成员不能自行升级角色。
- 只有组织负责人能创建邀请，发布者权限限制在指定组织和有效期内。
- 跳过校园认证可以进入公开浏览，但权限保持受限。
- 重置演示恢复游客状态且不保留虚构凭据。

## 7. 正式接口缺口

现有实现需要在接入该设计前修正：

1. 前端注册没有提交密码，后端会以验证码作为密码保存。注册请求必须明确要求密码并由服务端校验强度。
2. 前端声称支持验证码登录，现有后端却把 `code` 作为密码传给密码验证函数。必须增加独立 OTP 登录端点或暂时只保留密码登录。
3. 校园认证复用了注册验证码逻辑，没有独立 `purpose` 校验，也未看到学校域名白名单。应增加 `purpose=campus_verify`、域名配置、限流和尝试次数。
4. 尚无组织、组织成员、认证申请、角色邀请、有效期和审计日志的数据模型及 API。
5. JWT 需要刷新、撤销、设备退出与过期处理；前端不应把长期令牌当作永久登录依据。

## 8. 验证标准

- Node 状态测试覆盖第 6 节全部状态转换。
- 单文件 HTML 中所有脚本通过语法检查。
- 浏览器验证登录、注册、跳过认证、完成校园认证、提交组织申请、负责人邀请和无权限状态。
- 在 1366px 桌面与 390px 手机视口检查无横向溢出、无遮挡、按钮文字完整。
- 浏览器控制台无错误或警告。
- 页面始终明确标注本地模拟，不要求或传输真实账号、密码、验证码或证明文件。
